# 用户长期记忆体系设计方案

> 适用范围：微途旅行（WeiTu）TripAgent AI 子系统
> 相关包：`com.wtlx.infrastructure.memory.*`、`com.wtlx.domain.entity.memory.*`
> 表结构：PostgreSQL `vector_db`，DDL 见 `src/main/resources/db/schema-user-memory.sql`（唯一来源）

---

## 一、整体架构

### 1.1 两层记忆的边界（第一性划分）

本体系最核心的设计决策是**把"记忆"拆成两个作用域**，它们的载体、生命周期、检索方式完全不同：

| 维度 | 会话内短期记忆（SESSION） | 跨会话长期记忆（USER） |
| --- | --- | --- |
| 回答的问题 | 这一轮在聊什么 | 这个人是谁、偏好什么 |
| 作用域键 | `conversationId`（= `react_agent_` + threadId） | `subjectKey`（= `user:<userId>`，必须登录） |
| 存储载体 | `conversation_message` + `conversation_summary`（PG）<br>框架层 `MemorySaver`（JVM 内） | `user_memory`（PG + pgvector） |
| 生命周期 | 随会话，超阈值即摘要压缩 + 删除原文 | 跨会话累积，按状态机流转（ACTIVE → SUPERSEDED/EXPIRED） |
| 检索方式 | 直读（摘要 + 最近 8 轮） | **单路向量检索** |
| 写入方式 | 每轮同步追加 | 每累计 10 轮**异步子 Agent** 抽取该段会话记录 + 合并校验 |
| 失效模式 | 会话丢失 = 上下文断片 | 记忆污染 = 长期带偏用户画像 |

对应代码：
- 短期：`ConversationMemoryServiceImpl` + `ConversationMemoryInterceptor`（既有能力，本次未改动）
- 长期：`infrastructure/memory/**`（本次新增）
- 两者由 `ReactAgentConfig` 串联成一条拦截器链：**最终系统提示 = 长期记忆 + 对话摘要 + 原始提示词**

### 1.2 组件分层

```
                       ┌──────────────────────── 对话链路（在线，关键路径） ────────────────────────┐
GET /ai/react/trip/chat
   │                    MemorySubjectResolver ──► MemoryPrincipal(user:123)
   ▼                              │
AiController ──► TripAgentService.chatStream(message, threadId, requestId, principal)
   │                              │
   │                    RunnableConfig.metadata{ conversationId, subjectKey, cardSink }
   ▼                              │
ReactAgent.stream ──► [Interceptor 链]
                        ├─ ConversationMemoryInterceptor → 短期记忆（摘要 + 最近轮次）
                        └─ LongTermMemoryInterceptor    → MemoryContextBuilder
                                                             │
                                                             ▼
                                                  MemoryRetrievalService（单路向量召回）
                                                  └─ UserMemoryMapper.searchByVector（pgvector 余弦）
                        └─ MemoryRecallTool（模型按需主动召回）
   │
   ▼ SSE 流结束（finally 块）
ConversationMemoryService.appendAndCompressIfNeeded()   ← 短期记忆落库
MemoryExtractionService.extractAsync()                  ← 累计10轮触发，异步抽取该段会话记录
   │
   ▼（独立线程池 memoryExtractionExecutor）
MemoryLlmAgent（LLM 抽取 + 冲突校验）
   │
   ▼
MemoryMergeService（三级判定 + 分段锁）
   ├─ MemoryEmbeddingService（text-embedding-v3）
   └─ UserMemoryMapper
                        └────────────────────────────────────────────────────────────────────┘

        ┌──────────────────── 管理链路（离线，不参与对话） ────────────────────┐
        MemoryController (/ai/memory/**)     MemorySchemaInitializer（幂等 DDL）
        └──────────────────────────────────────────────────────────────────────┘
```

### 1.3 为什么这样切分

1. **在线与离线彻底分离**：抽取消耗 LLM（秒级），必须离开关键路径。对话链路只做"读记忆"（毫秒级），写入永远异步。用户感知不到记忆在增长。
2. **记忆是增强而非依赖**：`MemoryRetrievalService` 在 embedding 不可用时直接降级为空结果；PG/embedding 不可用时，Agent 仍能正常回答，只是不再个性化。
3. **写入必须有闸门**：抽取子 Agent 只有"读"权限，产出的是 `MemoryCandidate`；只有通过合并/冲突校验才可能变成 `UserMemory`。一次模型幻觉最多产出一个奇怪候选，无法直接篡改画像。

## 二、数据模型

### 2.1 `user_memory`（长期记忆主表）

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `id` | BIGSERIAL PK | 自增主键 |
| `memory_id` | UUID | **对外稳定标识**（取代关系、审计、按条删除都走它） |
| `subject_key` | VARCHAR(80) | **记忆主体键**，作用域边界，所有读写必带 |
| `user_id` | VARCHAR(64) | 登录用户 id（长期记忆已要求登录，恒有值） |
| `memory_type` | VARCHAR(24) | 12 类，见 `MemoryType` |
| `memory_key` | VARCHAR(96) | **归一化槽位键**（`budget.level` / `dietary.restriction`…），同槽位不同取值 = 潜在冲突 |
| `content` | TEXT | 自然语言断言，同时是向量化文本 |
| `structured` | JSONB | 结构化槽位值（可程序化读取） |
| `confidence` | REAL | 置信度 0~1，重复命中会巩固提升 |
| `importance` | REAL | 重要度 0~1，参与容量淘汰排序 |
| `status` | VARCHAR(16) | ACTIVE / SUPERSEDED / EXPIRED / DELETED |
| `source_type` / `source_ref` | VARCHAR | 来源类型 / 来源会话 |
| `evidence` | TEXT | 抽取依据原文（用户原句） |
| `valid_from` / `valid_to` | TIMESTAMP | 有效期；`valid_to IS NULL` = 长期有效（**稳定层**） |
| `superseded_by` | UUID | 被哪条记忆取代 |
| `version` | INT | 就地更新次数 |
| `hit_count` / `last_hit_at` | INT / TIMESTAMP | 复用强度（保留列，当前未用于清理，兼容历史数据） |
| `content_hash` | VARCHAR(64) | 内容指纹，抽取级幂等 |
| `dedup_key` | VARCHAR(200) | `type｜key｜valueHash`，库级去重键 |
| `embedding` | vector(1024) | 与业务列同表，一次 SQL 完成"向量排序 + 属性过滤" |
| `created_at` / `updated_at` | TIMESTAMP | |

**关键索引**

```sql
-- 生效记忆的唯一去重约束（部分索引：只约束 ACTIVE，历史行可保留同名键）
CREATE UNIQUE INDEX uk_user_memory_active_dedup
    ON user_memory (subject_key, dedup_key) WHERE status = 'ACTIVE';
-- 语义路 · 向量召回
CREATE INDEX idx_user_memory_embedding USING hnsw (embedding vector_cosine_ops);
-- 冲突校验（同槽位比对）/ 时效过滤 / 类型统计
CREATE INDEX idx_user_memory_subject_key  ON user_memory (subject_key, memory_key, status);
CREATE INDEX idx_user_memory_valid        ON user_memory (subject_key, status, valid_to);
CREATE INDEX idx_user_memory_subject_status ON user_memory (subject_key, status, memory_type);
```

**几个刻意的设计取舍**

- **为什么不复用 `vector_store` 表**：`vector_store` 只有 `(id, content, metadata, embedding)`，记忆需要的状态机、有效期、置信度、取代链、命中统计全都得塞进 `metadata` JSON，无法建索引、无法用窗口函数做容量收敛。独立建表让"向量排序 + 业务过滤"落在一条 SQL 里。
- **为什么用部分唯一索引而不是普通唯一索引**：被取代的历史行必须保留（审计与回溯），普通唯一索引会让"改口"写不进去。
- **为什么删除一律软删**：冲突判定的正确性依赖历史证据。用户说"我不吃辣了"，需要看得到"曾经喜欢吃辣"这条旧记录，否则无法解释也无法还原。
- **`embedding` 从实体中排除**：检索侧从不回读向量，回读一次等于白拉 4KB 并解析 1024 个浮点。写入通过 `embeddingLiteral` 透传字段完成。

### 2.2 `user_memory_extraction`（抽取台账）

`(subject_key, conversation_id, turn_hash)` 唯一 + `INSERT ... ON CONFLICT DO NOTHING`。

抽取是异步且可能重试的，同一用户还可能被多实例并行处理。台账把"同一轮只抽取一次"落到数据库层，而不是靠应用层先查后写（并发下必然失效）。

## 三、抽取与校验流程

### 3.1 触发点（段级，每累计 10 轮）

触发点在 `TripAgentServiceImpl` 的 `finally` 块——助手回复落库之后、SSE 关闭之前。**每轮只累计计数，不立即抽取**；当某会话累计满 `extraction-every-rounds`（默认 10）轮时，才异步抽取"该段会话记录"（最近 `segment-max-rounds` 轮），随后清零等待下一段：

```java
if (subjectKey != null && !answer.isEmpty()) {
    memoryExtractionService.extractAsync(subjectKey, conversationId);
}
```

`extractAsync` 立即返回，是否达到阈值由内存计数器判断；达标后任务提交到独立的 `memoryExtractionExecutor`（低并发 + 大队列 + `CallerRunsPolicy`）。

> 触发策略是写入链路简化的核心：从"每轮都抽"改为"每 10 轮抽一段"。要抽取的段直接从会话库取最近若干轮，不再依赖调用方逐轮透传文本。段触发器是内存计数器，单实例内准确，重启会丢失计数（最坏某段被多抽一次，由合并闸门去重吸收）。

### 3.2 记忆抽取 Agent（`MemoryLlmAgent.extractSegment`）

- **模型**：复用 `openAiChatModel`（百炼兼容模式），不额外引入模型配置；
- **输入**：当前时间 + 整段对话记录（用户 / 助手多轮往返，按时间正序，每条截断 600 字；助手发言标注"仅供参考，禁止作为用户偏好来源"）；
- **输出**：严格 JSON 数组，字段 `type / key / content / structured / confidence / importance / validTo / evidence`。

**提取完全基于 LLM，由 LLM 判断是否需要提取**：此前的前置启发式（偏好信号词表 + 长度阈值）已移除——是否值得抽取改由模型综合整段对话自行决定，整段都没有可沉淀信息时输出 `[]`，调用方据此跳过后续合并。提示词里保留的四条硬约束：

1. **划负样本**——明确列出"禁止抽取"：寒暄、复述、助手自己推荐的方案、通用常识、纯提问。这比只列正样本有效得多，尤其要挡住"把助手建议当用户偏好"这一类污染。
2. **槽位白名单 + 兜底**——给出 12 个既有槽位让同义信息收敛，同时允许自拟，否则模型会硬塞进不匹配的槽位，反而制造假冲突。
3. **相对时间绝对化**——"下个月""明年暑假"必须换算成 `yyyy-MM-ddTHH:mm:ss`，否则记忆永远有效，过期清理彻底失效。
4. **空数组是合法答案**——明说"整段都没有就输出 `[]`"，否则模型倾向硬凑，这是噪声记忆的主要来源。

**解析容错**（"先容错、再严格"）：去 Markdown 围栏 → 定位最外层 JSON（同时接受裸数组与 `{"memories":[...]}` 包装）→ 逐项转换。任何一项字段非法只丢该项，不影响整批。

### 3.3 合并与冲突校验（`MemoryMergeService`）

每条候选都必须先与已有记忆比对，得出五种决策之一才落库。**三级判定，先便宜后昂贵**：

```
候选
 │
 ├─① 指纹级（零 LLM 成本）
 │   dedup_key 精确命中  ────────────────────────► NOOP（巩固置信度）
 │
 ├─② 规则级
 │   存在同槽位记忆？ ──► 是 ──► 进入 ③（同槽位 = 同一件事的强信号）
 │   bestSim ≥ 0.92   ──► 是 ──► 内容更长 ? UPDATE（就地丰富）
 │                                        : NOOP
 │   bestSim < 0.60   ──► 是 ──► ADD
 │
 └─③ 模型级（仅灰区：同槽位 或 0.60 ≤ bestSim < 0.92）
     MemoryLlmAgent.judge ──► ADD / UPDATE / SUPERSEDE / FORGET / NOOP
         │ 失败 / 关闭
         └─► 保守规则：同槽位 → SUPERSEDE（以最新表述为准）；否则 ADD
```

**判定维度**（与人类整理笔记一致）：是不是同一件事 → 是不是互相矛盾 → 新的是否更具体 → 用户是否在否定旧说法。

提示词里刻意写死一句：**"话题相关不等于冲突"**。模型最容易犯的错是把"喜欢徒步"与"预算 3000"判成矛盾，进而错误覆盖用户偏好。

**五种决策的落地**

| 决策 | 语义 | 落地动作 |
| --- | --- | --- |
| `ADD` | 全新信息 | 插入 ACTIVE 新行 |
| `UPDATE` | 同槽位、同语义的补充 | 就地更新 `content` / `structured`，`version + 1`，置信度取大 |
| `SUPERSEDE` | 同槽位、语义矛盾（用户改口）| 旧行置 `SUPERSEDED` + `superseded_by` 指向新行 + `valid_to = now`（三重保证立刻退出检索），同时插入新行 |
| `FORGET` | 用户明确否定且新信息无需留存 | 旧行置 `EXPIRED` + `valid_to = now` |
| `NOOP` | 重复信息 | `confidence` 取大、追加证据、`updated_at` 刷新 |

**并发安全**

- 单实例内：Guava `Striped.lock(64)` 按主体键分段加锁，串行化"比对 + 决策 + 落库"；
- 跨实例：`uk_user_memory_active_dedup` 部分唯一索引兜底，捕获 `DataIntegrityViolationException` 转 NOOP；
- **已知限制**：分段锁只在单实例内有效。多实例部署下可能出现两条语义冲突的记忆同时生效——这是刻意取舍——为每轮对话引入分布式锁，代价高于收益。

## 四、检索链路集成

### 4.1 单路向量检索

`MemoryRetrievalService` 只保留语义向量一路：查询向量由 `MemoryEmbeddingService` **统一计算一次**后交给 `UserMemoryMapper.searchByVector`，按余弦相似度召回（阈值 `vector-threshold`，默认 0.45），直接构造成 `MemoryHit` 按相似度降序返回，再截断到 `retrieval-top-n`（默认 8）。

**为什么砍掉双路**：原先"语义路 + 关键词路"并行 + RRF 融合 + 画像兜底，实测维护成本高、收益有限——关键词路在高基 embedding 下大多召不回额外结果，画像兜底与向量路高度重叠。单路更简单、可预期，且仍满足"换个说法也能命中"的核心诉求。

**记忆是增强不是依赖**：embedding 不可用时，检索直接返回空列表，对话照常进行，绝不被记忆链路拖垮。

### 4.2 跨会话稳定复用（冷热分层）

检索是单路向量召回，命中后再由 `MemoryContextBuilder` 做**冷热分层**——稳定层（`valid_to IS NULL` 且类型属稳定层）与时效层分段，稳定层优先占额度、占用更多预算。这样高置信的长期偏好一旦被本轮问句向量召回，就优先进入上下文。

> 早期版本有独立的"画像兜底"：不依赖查询、强制把高价值画像顶进上下文，保证"新会话第一句没提偏好"也能带出画像。实测它与向量路高度重叠、维护成本高，已在本次瘦身中移除——代价是：若某条长期偏好与本轮问句语义无关，它可能不再被召回。这是为简化付出的明确代价。

### 4.3 上下文注入（两条通道）

**通道一 · 主动注入**（`LongTermMemoryInterceptor`）——模型无需思考就知道

`MemoryContextBuilder` 负责渲染，三层处理：

1. **冷热分层**：稳定层（`valid_to IS NULL` 且类型属稳定层）与时效层分段，稳定层优先占额度；
2. **预算裁剪**：按字符数硬裁剪（默认 900 字，稳定层最多 8 条 / 时效层 4 条），超出即停；
3. **冲突优先级声明**：提示头固定写入"若与本轮用户的明确表述冲突，一律以本轮为准"——长期记忆天然滞后于用户最新表达，不声明规则，模型可能坚持旧偏好而忽略用户刚说的话。

注入格式：

```
【用户长期记忆（跨会话沉淀）】
以下是从该用户以往对话中沉淀的历史偏好，用于个性化方案；若与本轮用户的明确表述冲突，一律以本轮为准。
■ 长期偏好
- [偏好] 用户喜欢徒步与自然风光（置信 0.85）
- [饮食偏好] 用户不吃辣（置信 0.90）
■ 时效信息
- [行程计划] 用户计划 2026-10 去成都（置信 0.80，有效期至 2026-10-31）
```

**通道二 · 被动召回**（`MemoryRecallTool`）——模型按需确认

对应"你还记得我的喜好吗""我之前说想去哪"这类元问题。主动注入解决"我应该知道什么"，被动召回解决"我需要确认什么"。只有被动召回会让用户感觉"系统真的记得我"，但只有主动注入才能保证模型规划行程时真的用上了偏好，两者缺一不可。

两条通道共用 `MemoryContextBuilder.render()`，避免"主动注入"与"主动查询"看到两种不同表述的记忆。

**身份传递**：`subjectKey` 与 `conversationId` 走同一条可靠通道——`RunnableConfig.metadata`。整条链路跑在 Reactor 线程上，ThreadLocal 传不过来。

### 4.4 记忆主体解析（`MemorySubjectResolver`）

**AI 对话已要求登录**。`/ai/**` 不再排除于 `LoginInterceptor` 之外，记忆主体**只有一个来源**：`UserHolder` 中的登录用户 id。

```java
UserDTO user = UserHolder.getUser();          // 由 RefreshTokenInterceptor 在入口建立
subjectKey = "user:" + user.getId();          // 再经 sanitizeSubjectKey 清洗并截断到 80 字符
```

| 环节 | 职责 |
| --- | --- |
| `RefreshTokenInterceptor` | 取 token 还原登录态写入 `UserHolder`；**优先 `authorization` 头，SSE 场景退到查询参数** |
| `LoginInterceptor` | `UserHolder` 为空直接 401——决定"是否登录"的唯一裁判 |
| `MemorySubjectResolver` | 只做 user id → `user:<userId>` 的转换，不做任何身份猜测 |

**两个不能省的细节**

1. **SSE 的 token 只能走查询参数**：浏览器原生 `EventSource` 无法设置任何请求头，这是协议限制而非产品取舍。`RefreshTokenInterceptor` 因此多读一路 `?token=`，但**两种通道拿到的是同一个 token**，后续 Redis 校验、TTL 刷新完全一致，不存在"弱一级"的身份。普通 `fetch`（历史 / 取消）照常带 `authorization` 头。
2. **解析必须发生在请求线程**：`UserHolder` 是 ThreadLocal，Reactor / ForkJoinPool 里读不到。故调用点固定在 Controller，结果经 `RunnableConfig.metadata` 往下游传递——这也是 §4.3「身份传递」那条通道存在的原因。

> **已移除的旧降级链**（2026-10-16）：`userId` 显式参数、`token`→Redis 回查、`clientId` 游客主体，共三条后备路径。
> 保留它们的代价很实在：`userId` 参数是直接读写他人记忆的越权通道；`clientId` 会让 token 临时失效的登录用户被静默判成游客，把偏好写进另一份互不相通的画像。
> 现在主体只有 `user:<userId>` 一种形态，没有匿名分支，也不再存在"这段请求到底属于谁"的歧义。

主体键经 `MemoryNormalizer.sanitizeSubjectKey()` 清洗（只保留字母数字 `_ : - .`）并截断到 80 字符——防止拼接进 Redis 键或 SQL 参数时引入噪音。

## 五、复用策略

### 5.1 跨会话稳定复用

| 机制 | 作用 |
| --- | --- |
| **主体键锚定到人** | 登录用户跨 threadId、跨会话、跨设备共享同一份画像（已移除游客按设备隔离的降级路径） |
| **冷热分层** | 高置信长期偏好被向量召回后优先进入上下文、占用更多预算 |
| **`confidence` 巩固** | 同一偏好被反复提及时置信度提升，排序与注入优先级随之提高 |
| **检索零缓存** | 刻意不做记忆结果缓存：记忆陈旧比多查一次库危险得多，一次带索引的排序本就是微秒级 |
| **时效退场** | `valid_to` 到点自动退出检索与注入，无需人工干预；行程类记忆用完即走 |
| **冲突以最新为准** | 用户改口时旧记忆立刻 `SUPERSEDED` + `valid_to = now`，三重保证新偏好立即生效 |

> 早期版本还做过"五级清理"（过期 / 低置信 / 容量 / 冗余合并 / 物理清除）与审计事件表，
> 实测维护成本高、收益有限，已在本次瘦身中整体移除。容量与冗余的收敛不再是自动进行的，
> 改为依赖抽取合并阶段的去重逻辑 + 用户手动清理（`DELETE /ai/memory`）兜底。

### 5.2 按需清理（用户可见）

| 场景 | 接口 |
| --- | --- |
| 删除单条记错的记忆 | `DELETE /ai/memory/{memoryId}`（软删） |
| 清空全部记忆（"忘记我"）| `DELETE /ai/memory`（物理删除，含历史行） |
| 观测系统记住了什么 | `GET /ai/memory/overview`、`GET /ai/memory/list` |

## 六、配置项（`trip-agent.memory.*`）

全部阈值集中配置，因为都需要按真实对话分布标定——**换 embedding 模型或换抽取模型必须重新标定**，否则会出现"该合并的没合并（冗余累积）"或"不该合并的被覆盖（偏好被误改）"。

| 分组 | 关键项 | 默认值 |
| --- | --- | --- |
| 总开关 | `enabled` | true |
| 抽取 | `extraction-enabled` / `extraction-every-rounds` / `segment-max-rounds` / `extraction-min-confidence` / `extraction-max-candidates` / `extraction-pool-size` | true / 10 / 10 / 0.35 / 8 / 2 |
| 合并 | `duplicate-similarity` / `conflict-similarity` / `conflict-judge-enabled` / `semantic-search-top-k` | 0.92 / 0.60 / true / 5 |
| 检索 | `retrieval-top-n` / `vector-top-k` / `vector-threshold` | 8 / 12 / 0.45 |
| 上下文 | `context-max-chars` / `stable-max-items` / `ephemeral-max-items` | 900 / 8 / 4 |

## 八、落地注意事项与已知限制

1. **向量维度必须与 RAG 一致**：`user_memory.embedding` 与 `vector_store.embedding` 同为 1024 维（`text-embedding-v3`），共用同一个 `dashscopeEmbeddingModel`。换模型时两处列定义与 `spring.ai.vectorstore.pgvector.dimensions` 需同步改。
2. **DDL 单一来源**：两张表（`user_memory` / `user_memory_extraction`）的 DDL 只存在于 `db/schema-user-memory.sql`，`MemorySchemaInitializer` 在启动期读取该脚本并按分号切分后逐条执行；同一份文件也可 `psql -f` 手工执行。失败只告警不阻断启动——PG 暂时不可用时服务仍应能提供不含长期记忆的对话能力。（早期版本把 DDL 同时写在 Java 常量数组与 `schema-postgresql.sql` 里，已合并为一份：两份副本必然漂移。）
3. **数据源不能走错**：记忆全部走 `aiJdbcTemplate`（PG）。`@Primary` 是 MySQL 业务数据源，走错的表现是"表不存在"并污染业务库。
4. **多实例限制**：合并阶段的锁是 JVM 内的分段锁，跨实例一致性依赖数据库唯一索引兜底。若将来要求强一致，需引入按主体的 Redis 分布式锁，但要评估对每轮对话的延迟影响。
5. **`MemorySaver` 是 JVM 内存实现**：`CardSink` 与记忆主体键都挂在 `RunnableConfig.metadata` 上，依赖它不做序列化。若将来换成持久化 Saver，需改为传可序列化标识再反查。
6. **成本控制两处埋点**：合并三级判定（指纹 → 规则 → 模型）、检索单次 embedding（每次检索只算一次查询向量）。抽取不再有前置启发式——是否抽取完全由 LLM 判断，段级触发（每 10 轮）而非每轮，从机制上把"每轮都可能付费"降为"每 10 轮才付费"。记忆是"按段付费"的开销，这两处比调提示词更能决定长期成本。
7. **检索调试入口**：`GET /ai/memory/search` 返回向量召回的命中与相似度，是判断"是否该调阈值"的主要抓手。上线后建议先观察一周命中分布再调参。
